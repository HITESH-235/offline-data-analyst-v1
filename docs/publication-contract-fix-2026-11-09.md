The previous planner requirements and execution arguments were separate dialects. Calendar requirements described grouping as ordinary `group_by` and derived measures, while execution emitted calendar state. Payment coverage could calculate the right values in grouped rows without binding them to scalar requirements. Unsupported distinct count could be changed to ordinary count while keeping a distinct label. Empty filters had conflicting meanings. Reference detection could treat an explicit standalone question as a follow-up merely because it contained “that.”

**Implementation.** [operations.py](/home/hit235/Projects/offline-data-analyst/server/app/analysis/operations.py) defines strict typed operation parameters and generates the planner's discriminator-linked schema and fallback tool schemas. New supported requests return an executable `analysis_plan`: named outputs, their actual operation parameters, resolved sources, and separate chart scope. The same registry validates, executes and supplies publication evidence. The planner no longer asks another model turn to invent equivalent tool arguments or factual prose for these supported operations.

[planned_analysis.py](/home/hit235/Projects/offline-data-analyst/server/app/services/planned_analysis.py) resolves catalog IDs and declared relationships, retains grain guards, executes each named population, and binds the exact operation to completion requirements. Calendar parameters preserve date column, years, comparison mode, formula, filters and units. Known associative arithmetic forms have a canonical identity; execution values are not edited to match an oracle. Source tables and join keys are independently checked. A calendar comparison requires at least two resolved years; inheritance checks retain the requested/reference years and unchanged source/formula/filter fields.

Registry evidence includes the typed operation and a digest of the produced result. That prevents later swapping or modifying rows, units or provenance; a digest alone is **not** mathematical verification or proof of natural-language understanding. Independent SQLite comparisons provide the numeric checks reported below. Existing legacy inputs remain supported through explicit adapters and domain checks, not exemptions from completion requirements.

[output_bindings.py](/home/hit235/Projects/offline-data-analyst/server/app/analysis/output_bindings.py) can project a verified, fully selected group into a named scalar requirement. It checks source, original predicates, measure identity, units, transformations, one-group selection and literal types. It cannot sum overlapping distinct counts or discard predicates. Projection evidence is saved with the output. Correct quarterly values and equivalent coverage counts therefore need not fail solely because their representation differs.

`count_distinct` is implemented and verified as a distinct non-null count, including custom Python exports of the canonical aggregation operation. The frontend recognizes its aggregation provenance as a measure. Ordinary counts cannot use a Distinct Count label or satisfy a distinct-count requirement, including incomplete results. Empty and omitted predicate lists are consistent no-ops; nonempty predicates are retained and validated. Optional null metadata is normalized without removing a literal null predicate. A literal comparison and a column-reference comparison have distinct operands; `value_column: null` is not a second operand. Calendar-day normalization applies to both literal-date and column-date comparisons, including boundary days. Cross-database joins receive an explicit unsupported-operation explanation without a fabricated mapping or count.

Planner validation errors identify JSON paths. Rejected output is retained in sanitized diagnostics, with credential fields and key-shaped values redacted. There is at most one planner schema-repair attempt using the actual error and original request. Semantic guards prevent a repair from changing known source, formula, measure identity, units or transformations merely to obtain accepted JSON. Provider failures do not trigger schema retries. The fallback agent's correction budget is bounded as well.

Successful context and unfulfilled typed request intent are stored separately. Failed comparisons never become successful context. New planning uses an explicit standalone/inherit/clarify decision instead of the broad keyword fallback. Clarifications have a distinct terminal progress state, rather than claiming an analysis completed.
